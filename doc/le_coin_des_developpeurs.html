Le coin des développeurs

WhiteCat est un logiciel libre, sous licence GNU GPL v2. Créé par Christoph Guillermet (2009-2016), il est repris et modernisé depuis 2026 par Jacques Bouault (arpschuino.fr) : passage à SDL2 et RtMidi, portage Linux et Raspberry Pi, moteur 16 bits, gestion des projecteurs (devices).

Cette page explique comment récupérer les sources, les compiler et proposer vos modifications. Toute contribution est bienvenue : correction de bug, nouvelle fonction, documentation, traduction, tests.

Échanger avec nous

Pour signaler un bug, poser une question, proposer une idée ou annoncer que vous travaillez sur quelque chose, rendez-vous sur le forum :

  • https://forum.arpschuino.fr/viewforum.php?f=24

Pour un bug, indiquez la version de WhiteCat (affichée au démarrage), votre système (Windows 10/11, Linux, Raspberry Pi), ce que vous faisiez, ce que vous attendiez et ce qui s'est passé. Si vous n'arrivez pas à compiler, joignez la sortie complète de build.bat : c'est souvent un détail d'environnement, vite réglé.

Récupérer les sources

Le code est sur GitHub : https://github.com/arpschuino/whitecat_crossplateform 

git clone https://github.com/arpschuino/whitecat_crossplateform.git
cd whitecat_crossplateform

Deux branches principales :

  • 0.9.2 (branche par défaut) : la version stable. Les corrections de bugs partent d'ici.
  • 0.10-devices : la version en développement (patch 16 bits, devices et import GDTF, Control Fixtures, moteur 16 bits). Les nouvelles fonctions partent d'ici.

Attention : un spectacle enregistré en 0.10 ne se rouvre pas correctement en 0.9.2. Gardez des dossiers séparés pour chaque version.

Compiler sous Windows

Le compilateur, les bibliothèques et les fichiers nécessaires à l'exécution ne sont pas dans git : ils sont fournis par un kit de build (environ 80 Mo), qu'un script télécharge et installe pour vous. 

setup_windows.bat
build.bat

L'exécutable est produit dans whitecatbuild\build\white_cat_for_mingw\Whitecat_Crossplatform.exe, à côté des DLL, des polices et de la configuration.

Le kit installe :

  • tools/MinGW/ : le compilateur TDM-GCC 5.1.0 (32 bits). N'utilisez pas un autre compilateur : les bibliothèques fournies sont compilées pour celui-ci.
  • whitecatlib/ : SDL2 2.30.8, SDL2_ttf 2.24.0, SDL2_image 2.8.8, SDL2_mixer 2.8.1, RtMidi 6.0.0, OpenCV 2.4.8, libharu, zlib, FTDI D2XX. C'est une copie réduite du dépôt whitecatlib de Christoph, complétée par SDL2 et RtMidi.
  • whitecatbuild/build/white_cat_for_mingw/ : DLL, polices, ressources et configuration par défaut.

Bon à savoir :

  • setup_windows.bat n'écrase jamais un fichier existant : vos réglages (user/) et vos spectacles (saves/) sont conservés si vous le relancez.
  • Si vous aviez déjà reconstitué vous-même whitecatlib/ ou tools/, renommez-les avant de lancer le script : sinon, il compléterait votre version au lieu d'installer celle du kit.
  • Sans connexion : téléchargez le kit depuis la page Releases, posez le zip à côté de setup_windows.bat, puis lancez le script.
  • Avec VSCode : ouvrez le dossier du projet, Ctrl+Shift+B compile, F5 lance le débogueur.

Compiler sous Linux

Sous Linux (x86_64 ou Raspberry Pi), les bibliothèques viennent des paquets du système : 

sudo apt install build-essential libsdl2-dev libsdl2-ttf-dev libsdl2-image-dev libsdl2-mixer-dev \
                 libhpdf-dev libasound2-dev libftdi1-dev zlib1g-dev
make -f Makefile.linux -j4

L'exécutable est produit dans whitecatbuild/build/linux/Whitecat_Crossplatform. Copiez à côté de lui les dossiers d'exécution (Fonts/, gfx/, ressources/, user/…) pris dans l'archive Linux de la dernière release. Sous Linux, la casse des noms de fichiers compte : utilisez bien ceux de l'archive Linux.

Se repérer dans le code

Tout le code est dans Src/. Quelques points d'entrée :

  • MAIN.cpp : initialisation et boucle principale.
  • graphics_backend.h : la couche SDL2 qui remplace Allegro et OpenLayer (fenêtre, dessin, clavier, souris).
  • midi_backend.h (RtMidi), audio_backend.h (SDL2_mixer, lecteurs OGG/FLAC), wc_platform.h (différences Windows / Linux).
  • save_show.cpp : enregistrement et chargement des spectacles.
  • Les fichiers *_core.cpp contiennent la logique d'une fenêtre, les fichiers *_visu.cpp son dessin (séquentiel, faders, bangers, grid players, patch…).

Le code hérité est dense, avec beaucoup de variables globales. Trois pièges à connaître :

  • En-tête précompilé : si vous modifiez graphics_backend.h, ou un en-tête inclus par whitecat.h, supprimez Src/wc_tus.h.gch avant de recompiler.
  • Nouvelle variable globale dans graphics_backend.h : suivez le modèle WC_SKIP_GLOBALS (déclaration extern dans les fichiers, définition dans MAIN.cpp). Sinon, chaque fichier aurait sa propre copie, sans erreur de compilation.
  • Changement de branche (0.9.2 ↔ 0.10-devices) : supprimez les fichiers *.o et *.d de whitecatbuild/build/white_cat_for_mingw/ et le fichier .gch, sinon l'exécutable mélangerait les deux versions.

Proposer une modification

On passe par un fork et une pull request :

  1. Sur GitHub, cliquez sur Fork en haut de la page du dépôt : vous obtenez votre propre copie.
  2. Clonez votre fork, et déclarez le dépôt d'origine sous le nom upstream : 
    git clone https://github.com/VOTRE_COMPTE/whitecat_crossplateform.git
cd whitecat_crossplateform
git remote add upstream https://github.com/arpschuino/whitecat_crossplateform.git
  3. Créez une branche pour votre travail, à partir de 0.9.2 pour une correction, ou de 0.10-devices pour une nouvelle fonction : 
    git checkout -b correction-affichage-crossfade upstream/0.9.2
  4. Travaillez, compilez, testez. Enregistrez par petites étapes : 
    git status
git add Src/fichier_modifie.cpp
git commit -m "Sequentiel : corrige l'affichage du crossfade apres un GO BACK"
  5. Avant de proposer, récupérez les nouveautés du dépôt d'origine : 
    git fetch upstream
git rebase upstream/0.9.2
  6. Envoyez votre branche sur votre fork, puis ouvrez une pull request depuis GitHub : 
    git push origin correction-affichage-crossfade

Pour qu'une pull request soit facile à relire :

  • un sujet par pull request, avec des commits courts et un message qui dit ce qui change et pourquoi ;
  • décrivez comment vous avez testé (Windows, Linux, avec quel matériel DMX ou MIDI) ;
  • ne committez ni whitecatlib/, ni tools/, ni vos spectacles : ils sont exclus par .gitignore, laissez-les dehors ;
  • pour un changement important, parlez-en d'abord sur le forum : on évitera de travailler deux fois sur la même chose.

Vos contributions sont publiées sous la même licence que WhiteCat, la GNU GPL v2.

Commenter le code (Doxygen)

Une partie du code est commentée au format Doxygen, qui génère une documentation technique à partir des commentaires. Pour une nouvelle fonction, merci de suivre ce format : 

/**
 * \brief Lit un fichier audio a partir d'un instant donne
 * \param file      chemin complet du fichier (wav, mp3, ogg, flac)
 * \param startTime debut de la lecture, en millisecondes
 * \return numero du fichier dans la playlist, -1 en cas d'erreur
 */
int play(const char* file, long startTime);

Les commentaires en // restent des commentaires ordinaires, ignorés par Doxygen. Pour générer la documentation (dans docAPIwhitecat/, à côté du dépôt) : 

cd Src
doxygen Doxyfile

Un peu d'histoire

WhiteCat est passé en open source en juin 2013. Georges Khaznadar, Anton Langhoff et RuiSerge ont alors mis en place le dépôt Git, les conventions Doxygen et les premières règles de contribution, sur le dépôt de Christoph Guillermet. Cette page remplace leurs pages de 2013-2014, devenues obsolètes avec la modernisation du logiciel, mais l'esprit reste le même : travailler à plusieurs sans jamais perdre une version qui marche.
